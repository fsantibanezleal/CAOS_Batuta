# Budgets and memory

This guide measures what loads at the start of every session, fixes a CLAUDE.md that grew past its budget by moving text to
the tiers where it belongs, and keeps an auto-memory index inside the 200-line load. The reasoning, the limits and their
sources are in [context tiers and budgets](../concepts/context-tiers.md). Output is real, captured in a throwaway project and a
fake home folder; paths are omitted or shown as `<project>`. In the transcripts `batuta` stands for
`python <plugin folder>/scripts/batuta.py`.

## 1. Measure

`context measure` prints each always-loaded file with its layer, bytes and an estimated token count (bytes divided by 4, an
estimate and labelled as one). `--home DIR` names the folder that holds `.claude/` and `--chain-root DIR` stops the CLAUDE.md
chain there, so you can measure one project without the CLAUDE.md files of its parent folders:

```
batuta context measure --project . --home <fake home> --chain-root .
OK L0 user core: 4900 bytes, about 1225 tokens (estimate) (<fake home>/.claude/CLAUDE.md)
OK L0 project core: 7928 bytes, about 1982 tokens (estimate) (<project>/CLAUDE.md)
total at session start (L0): 12828 bytes, about 3207 tokens (estimate: bytes / 4); L1 files load only with a matching file
```

The user core here is the shipped generic template rendered by `init user` with default values (4900 bytes). `measure` always
exits 0 and lists every `@path` import as its own L0 row, because imports load at launch. For the real figure in a live
session, `/context` shows what loaded and `/usage` shows the prompt-cache line (https://code.claude.com/docs/en/costs); the
`measure` estimate is for budgeting, not for billing.

## 2. Check against the budgets

`context check` measures bytes against the `budgets` of `batuta.json` (defaults: user core 7000 bytes, project core 7000,
unscoped rules 2000, memory index 4000 bytes and 60 lines). In the throwaway project the CLAUDE.md had a long deployment
runbook and a list of style notes:

```
batuta context check --project . --home <fake home> --chain-root .
OK user core (CLAUDE.md): 4900 of 7000 bytes (about 1225 tokens, estimate) (<fake home>/.claude/CLAUDE.md)
FAIL project CLAUDE.md chain is 7928 bytes, over the budget 7000 by 928; largest sections: "Deployment runbook" in CLAUDE.md (5249 bytes), "Style notes" in CLAUDE.md (2658 bytes); demote them to a reference file listed in the index (L2, read on demand) or a path-scoped rule (L1)
OK SKIP no memory folder for project
context check: budgets exceeded
```

Exit 1. Exactly at a limit passes; one byte over fails. The message names the largest sections and where to move them. Never
raise a budget to make the check pass: the budget exists because the text is paid by every session and every subagent that loads
it.

## 3. Move text to the right tier

Rules of thumb (from the concept page): a statement that must hold in every task stays in the core as one line plus a pointer; a
statement tied to files becomes a path-scoped rule (L1); procedure text becomes a knowledge unit read by trigger (L2); anything
that must be blocked becomes a hook.

Write each moved section as a file under `.batuta/knowledge/units/` and describe it in the manifest `.batuta/knowledge/manifest.json`
(contract C12). Here the runbook is read when the task mentions deploying, and the style notes only when a file under `src/`
is read:

```json
{
  "contract_version": "1.0",
  "budget": {"core_bytes": 7000, "index_bytes": 4000},
  "units": [
    {"id": "deploy-runbook", "title": "Deployment runbook", "kind": "procedure", "file": "units/deploy-runbook.md",
     "summary": "The steps to deploy each host and what to check afterwards.", "load": "trigger", "triggers": ["deploy", "host"]},
    {"id": "style-notes", "title": "Style notes", "kind": "rule", "file": "units/style-notes.md",
     "summary": "Keep functions short and name them for what they return.", "load": "path", "paths": ["src/**"]}
  ]
}
```

A summary is at most 160 characters; `requires` lists units that must be read with this one, and a cycle is refused. Render into
`.claude` so Claude Code finds the path-scoped stub under `.claude/rules/` (the links are written relative to where each page
lands):

```
batuta context build --manifest .batuta/knowledge/manifest.json --out .claude --apply
NEW CORE.md
NEW INDEX.md
NEW rules/style-notes.md
context build: written; core 164 bytes (about 41 tokens, estimate), index 487 bytes
```

`.claude/rules/style-notes.md` is a stub:

```
---
paths:
  - "src/**"
---
<!-- generated by batuta context build -->
# Style notes

Keep functions short and name them for what they return.

Full text: `../../.batuta/knowledge/units/style-notes.md`; read it when this rule applies.
```

and `.claude/INDEX.md` lists every unit with its load rule, in the style of llms.txt. Replace the two sections of CLAUDE.md with
one line that points at the index, then check again:

```
batuta context check --project . --home <fake home> --chain-root .
OK user core (CLAUDE.md): 4900 of 7000 bytes (about 1225 tokens, estimate) (<fake home>/.claude/CLAUDE.md)
OK project CLAUDE.md chain: 154 of 7000 bytes in 1 file(s)
OK SKIP no memory folder for project
context check: within budget
```

The project core went from 7928 to 154 bytes. Running `context build --apply` a second time reports `SAME` for every file, because
the output is sorted, LF only and carries no timestamp; that keeps the cached prefix reusable. `context build` refuses with
`REFUSED` if the core or the index exceeds the manifest budget, and warns when the core exceeds the C01 `user_core_bytes`.

Install the same stubs for the user level with `device restore --stubs ~/.claude/rules`, which rewrites each link so it
resolves from there.

## 4. Keep the memory index small

Claude Code loads only the first 200 lines or 25 KB of a project's `MEMORY.md` at every session start. `memory index` rewrites
the index as pinned lines plus one line per topic and moves the per-memory lines to topic pages, opened only when their topic
matches. It needs a topics file (contract C13) that lists the project; a project that is not listed is not opted in and exits 2
with nothing written. A topics file for one project:

```json
{
  "contract_version": "1.0", "version": 1, "hook_max_chars": 110, "title_max_chars": 60,
  "projects": {
    "Demo": {
      "pinned": ["feedback_decide_and_act"],
      "topics": [
        {"id": "deploy", "title": "Deploy and hosts", "when": "before deploying or touching a host", "match": ["deploy", "staging"]},
        {"id": "release", "title": "Release", "when": "before tagging or promoting", "match": ["release"]}
      ],
      "other": {"title": "Other", "when": "when no topic above fits"}
    }
  }
}
```

Each `match` entry is a regular expression searched in the memory file's name without `.md` (its stem); a pinned memory stays in the index, and any other memory goes to the first topic whose pattern matches, else to `other`. Real output on a folder of five
memories, dry run then applied (the dry run lists what would change):

```
batuta memory index --memory-dir memory --project Demo --topics topics.json
OK 5 memories in 3 topic page(s); index 454 bytes, 7 lines (budget 4000 bytes, 60 lines)
CHANGED MEMORY.md
NEW topics/deploy.md
NEW topics/release.md
NEW topics/other.md
memory index: dry run, nothing written (use --apply)
```

The rewritten index:

```
# Memory index (generated by batuta memory index; edit the memories or the topics file, not this file)
## Always relevant
- [Decide and act](feedback_decide_and_act.md) - decide the next step and do it
## Topics (open the page when the task matches)
- [Deploy and hosts (2)](topics/deploy.md) - before deploying or touching a host
- [Release (1)](topics/release.md) - before tagging or promoting
- [Other (1)](topics/other.md) - when no topic above fits
```

and a topic page, `topics/deploy.md`:

```
# Deploy and hosts
<!-- generated by batuta memory index -->

Read when: before deploying or touching a host.

- [Deploy checklist](../project_deploy_checklist.md) - the steps to deploy the service to the staging host
- [Staging host notes](../project_staging_notes.md) - ports, users and where the logs live on staging
```

A second `--apply` reports `SAME` for the index and every page. The command writes, replaces and removes only pages that carry
its generation mark (`<!-- generated by batuta memory index -->`); a file in `topics/` without the mark is yours and is never
read as a source of entries, never removed, and when its name is the page of a topic that has members the run fails and names
the file. Pages written by an older tool before the mark existed are migrated with `--adopt-legacy`. Memory folders are found
under `<home>/.claude/projects/<sanitized project path>/memory`, where every character of the project path that is not a letter
or digit becomes a hyphen. A memory index that is over 200 lines or 25 KB fails `context check` for any project.

## 5. Keep skills and agents cheap

The 13 skills list 2008 characters in total, measured as name plus description plus `when_to_use` per skill
(`tests/test_skills_content.py`). A skill you add costs a listing line at every session start; give it a short, trigger-first
description, set `disable-model-invocation: true` on a procedure with side effects (the plugin does it for `freeze` and
`promote`), and use `skillOverrides` with `name-only` for a rarely used skill. `/doctor` estimates the listing cost
(https://code.claude.com/docs/en/skills). The two haiku roles skip CLAUDE.md entirely (`omitClaudeMd: true`).

The skill `context-audit` runs steps 1 to 4 of this guide in a session.
